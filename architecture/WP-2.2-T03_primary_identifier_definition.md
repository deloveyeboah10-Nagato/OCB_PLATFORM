# WP-2.2-T03 — Define Primary Identifiers

**Programme:** OCB Platform v1.0.0
**Work Package:** WP-2.2 — Logical Data Model
**Ticket:** WP-2.2-T03
**Status:** **REVISED / RECONCILED / LOCKED**
**Decision Type:** Logical data-model definition

---

# 1. Purpose

This ticket defines the authoritative primary identifiers for all relational entities established in **WP-2.2-T01** and whose attributes were defined and reconciled with the physical deployment in **WP-2.2-T02**.

The primary-key model is explicitly aligned with the approved **WP-2.4 physical table deployment**.

Each entity has a primary identifier appropriate to its own relational grain.

Primary identifiers establish the identity of rows within their respective entities. They do not imply that identifiers with the same attribute name across different institutional schemas represent the same real-world object.

The primary-key model must also be understood together with the authoritative **12 foreign-key relationships** defined in WP-2.2-T02.

---

# 2. OCB Primary Identifiers

## 2.1 `OCB_CUSTOMER`

`OCB_CUSTOMER` represents an OCB-resolved cross-institutional customer identity.

| Entity         | Primary Identifier | Role        | Status  |
| -------------- | ------------------ | ----------- | ------- |
| `OCB_CUSTOMER` | `ocb_customer_id`  | Primary key | 🔒 LOCK |

`ocb_customer_id` is the primary key of:

```text
ocb.customer
```

It provides the stable OCB-level identity to which institutional customer identities may be mapped.

It is independent of the customer identifiers generated by Ananse, SikaCredit, and Oman Remit.

---

## 2.2 `OCB_CUSTOMER_IDENTITY`

`OCB_CUSTOMER_IDENTITY` represents the relationship between an OCB-resolved identity and an institutional source-system customer identity.

The primary key is:

```text
(source_entity, source_customer_id)
```

| Attribute            | Role                                         | Status  |
| -------------------- | -------------------------------------------- | ------- |
| `source_entity`      | Component of composite primary key           | 🔒 LOCK |
| `source_customer_id` | Component of composite primary key           | 🔒 LOCK |
| `ocb_customer_id`    | Foreign key → `ocb.customer.ocb_customer_id` | 🔒 LOCK |

Therefore:

```text
PRIMARY KEY
(source_entity, source_customer_id)
```

while:

```text
ocb_customer_id
        ↓
ocb.customer.ocb_customer_id
```

is a foreign-key relationship.

This distinction is mandatory.

`ocb_customer_id` identifies the resolved OCB customer to which the source identity is mapped; it does not uniquely identify the source identity mapping itself.

# 3. Ananse Primary Identifiers

## 3.1 `ANANSE_CUSTOMER`

`ANANSE_CUSTOMER` represents a customer record maintained by Ananse.

| Entity            | Primary Identifier | Role        | Status  |
| ----------------- | ------------------ | ----------- | ------- |
| `ANANSE_CUSTOMER` | `customer_id`      | Primary key | 🔒 LOCK |

`customer_id` uniquely identifies an Ananse customer within:

```text
ananse.customer
```

It is institution-owned and must not be interpreted as an OCB-wide customer identifier.

---

## 3.2 `ANANSE_WALLET`

`ANANSE_WALLET` represents an Ananse wallet.

| Entity          | Primary Identifier | Role        | Status  |
| --------------- | ------------------ | ----------- | ------- |
| `ANANSE_WALLET` | `wallet_id`        | Primary key | 🔒 LOCK |
| `ANANSE_WALLET` | `customer_id`      | Foreign key | 🔒 LOCK |

`wallet_id` uniquely identifies an Ananse wallet within:

```text
wallet.wallet
```

The wallet's `customer_id` does not form part of the primary key.

It establishes the wallet-to-customer relationship:

```text
ananse.customer.customer_id
            │
            │ FK
            ▼
wallet.wallet.customer_id
```

The wallet therefore remains independently identifiable from the customer.

---

## 3.3 `ANANSE_TRANSACTION`

`ANANSE_TRANSACTION` represents an individual Ananse transaction/activity record.

| Entity               | Primary Identifier | Role        | Status  |
| -------------------- | ------------------ | ----------- | ------- |
| `ANANSE_TRANSACTION` | `transaction_id`   | Primary key | 🔒 LOCK |

`transaction_id` uniquely identifies an individual transaction within:

```text
ananse.transaction
```

The transaction's customer and wallet identifiers are foreign keys and are not components of the transaction primary key.

The relevant relationships are:

```text
customer_id
    ↓
ananse.customer.customer_id
```

and:

```text
wallet_id
    ↓
wallet.wallet.wallet_id
```

The reference identifiers are likewise foreign keys and do not form part of the transaction primary key:

```text
transaction_type_id
transaction_status_id
transaction_channel_id
currency_id
```

Therefore the transaction remains independently identifiable by:

```text
transaction_id
```

regardless of its customer, wallet, transaction type, status, channel, or currency.

# 4. SikaCredit Primary Identifiers

## 4.1 `SIKACREDIT_CUSTOMER`

`SIKACREDIT_CUSTOMER` represents a customer record maintained by SikaCredit.

| Entity                | Primary Identifier | Role        | Status  |
| --------------------- | ------------------ | ----------- | ------- |
| `SIKACREDIT_CUSTOMER` | `customer_id`      | Primary key | 🔒 LOCK |

`customer_id` uniquely identifies a SikaCredit customer within:

```text
sikacredit.customer
```

It is independent of:

```text
ANANSE_CUSTOMER.customer_id
OMAN_REMIT_CUSTOMER.customer_id
OCB_CUSTOMER.ocb_customer_id
```

Identical literal values across institutions do not imply identity equivalence.

---

## 4.2 `SIKACREDIT_LOAN`

`SIKACREDIT_LOAN` represents an individual loan issued by SikaCredit.

| Entity            | Primary Identifier | Role        | Status  |
| ----------------- | ------------------ | ----------- | ------- |
| `SIKACREDIT_LOAN` | `loan_id`          | Primary key | 🔒 LOCK |
| `SIKACREDIT_LOAN` | `customer_id`      | Foreign key | 🔒 LOCK |

`loan_id` uniquely identifies the loan within:

```text
sikacredit.loan
```

The `customer_id` attribute establishes the relationship to:

```text
sikacredit.customer.customer_id
```

It is therefore a foreign key and is not part of the loan primary key.

The loan remains independently identifiable regardless of the customer associated with it.

---

## 4.3 `SIKACREDIT_REPAYMENT`

`SIKACREDIT_REPAYMENT` represents an individual repayment against a SikaCredit loan.

| Entity                 | Primary Identifier | Role        | Status  |
| ---------------------- | ------------------ | ----------- | ------- |
| `SIKACREDIT_REPAYMENT` | `repayment_id`     | Primary key | 🔒 LOCK |
| `SIKACREDIT_REPAYMENT` | `loan_id`          | Foreign key | 🔒 LOCK |

`repayment_id` uniquely identifies an individual repayment within:

```text
sikacredit.repayment
```

`loan_id` establishes the relationship:

```text
sikacredit.loan.loan_id
            │
            │ FK
            ▼
sikacredit.repayment.loan_id
```

`loan_id` is not part of the repayment primary key.

This permits multiple repayment records to belong to the same loan:

```text
loan_id = LN-001
    │
    ├── repayment_id = RP-001
    ├── repayment_id = RP-002
    ├── repayment_id = RP-003
    └── repayment_id = RP-004
```

# 7. Primary-Key and Foreign-Key Separation

Primary keys and foreign keys serve different purposes.

A primary key answers:

```text
"What row/object is this?"
```

A foreign key answers:

```text
"What existing row/object is this related to?"
```

Accordingly:

```text
ANANSE_WALLET
    wallet_id       → PK
    customer_id     → FK
```

```text
ANANSE_TRANSACTION
    transaction_id          → PK
    customer_id             → FK
    wallet_id               → FK
    transaction_type_id     → FK
    transaction_status_id   → FK
    transaction_channel_id  → FK
    currency_id             → FK
```

```text
SIKACREDIT_LOAN
    loan_id         → PK
    customer_id     → FK
```

```text
SIKACREDIT_REPAYMENT
    repayment_id    → PK
    loan_id         → FK
```

```text
OMAN_REMIT_REMITTANCE
    remittance_id   → PK
    customer_id     → FK
    country_id      → FK
```

```text
OCB_CUSTOMER_IDENTITY
    (source_entity, source_customer_id) → PK
    ocb_customer_id                     → FK
```

The physical deployment therefore does not use foreign-key attributes as substitutes for primary identifiers.

# 9. Identifier Principles

## 9.1 Entity-specific identity

Each primary identifier identifies the object represented by its entity.

```text
ocb_customer_id  → OCB-resolved identity
customer_id      → institutional customer
wallet_id        → wallet
transaction_id   → transaction
loan_id          → loan
repayment_id     → repayment
remittance_id    → remittance
```

No identifier is reused to represent a different object merely because the objects are related.

---

## 9.2 Institutional customer identifiers remain institution-owned

The following identifiers are independently scoped:

```text
ananse.customer.customer_id

sikacredit.customer.customer_id

oman_remit.customer.customer_id
```

The fact that all three are named `customer_id` does not make them globally identical.

For example:

```text
ANANSE       CUST-001
SIKACREDIT   CUST-001
OMAN_REMIT   CUST-001
```

represent three distinct source identities unless OCB explicitly resolves them to the same:

```text
ocb_customer_id
```

---

## 9.3 Composite primary identity for source mapping

`OCB_CUSTOMER_IDENTITY` uses:

```text
(source_entity, source_customer_id)
```

as its primary key because `source_customer_id` alone is not sufficient to uniquely identify a source identity across multiple institutions.

For example:

```text
ANANSE + CUST-001
SIKACREDIT + CUST-001
OMAN_REMIT + CUST-001
```

are distinct source identities.

The `source_entity` component therefore forms an essential part of the mapping entity's primary key.

---

## 9.4 Foreign keys do not redefine entity identity

A child entity's foreign key identifies its relationship to another entity.

It does not automatically become part of the child entity's primary key.

For example:

```text
wallet_id       → PK
customer_id     → FK
```

and:

```text
transaction_id  → PK
wallet_id       → FK
customer_id     → FK
```

The physical deployment therefore maintains independent row identity for wallets and transactions.

# 10. Reconciliation With Physical Deployment

This revision explicitly aligns the logical primary-key model with the approved physical deployment.

The following primary keys are authoritative:

```text
ocb.customer
    PK → ocb_customer_id

ocb.customer_identity
    PK → (source_entity, source_customer_id)

ananse.customer
    PK → customer_id

wallet.wallet
    PK → wallet_id

ananse.transaction
    PK → transaction_id

sikacredit.customer
    PK → customer_id

sikacredit.loan
    PK → loan_id

sikacredit.repayment
    PK → repayment_id

oman_remit.customer
    PK → customer_id

oman_remit.remittance
    PK → remittance_id
```

The foreign-key relationships associated with these identifiers are those defined in the **12-FK physical relational structure**.

No alternative primary identifiers are introduced.

No FK is incorrectly promoted to a primary identifier.

No existing primary identifier is replaced merely because another entity references it.

# 11. Final Decision

The primary identifiers defined in this ticket are the authoritative primary-key baseline for the OCB Platform v1.0.0 relational model.

They are reconciled with:

* **WP-2.2-T01 — Define Relational Entities**;
* **WP-2.2-T02 — Define Attributes**;
* the approved **WP-2.4 physical table deployment**; and
* the authoritative **12-FK relational structure**.

The authoritative primary-key model is therefore:

```text
OCB_CUSTOMER
    PK: ocb_customer_id

OCB_CUSTOMER_IDENTITY
    PK: (source_entity, source_customer_id)
    FK: ocb_customer_id

ANANSE_CUSTOMER
    PK: customer_id

ANANSE_WALLET
    PK: wallet_id
    FK: customer_id

ANANSE_TRANSACTION
    PK: transaction_id
    FKs: customer_id
         wallet_id
         transaction_type_id
         transaction_status_id
         transaction_channel_id
         currency_id

SIKACREDIT_CUSTOMER
    PK: customer_id

SIKACREDIT_LOAN
    PK: loan_id
    FK: customer_id

SIKACREDIT_REPAYMENT
    PK: repayment_id
    FK: loan_id

OMAN_REMIT_CUSTOMER
    PK: customer_id

OMAN_REMIT_REMITTANCE
    PK: remittance_id
    FKs: customer_id
         country_id
```

No subsequent logical-model ticket may introduce an alternative primary identifier without explicitly reopening this decision.
